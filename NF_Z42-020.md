# Secure Capture Journal with Certified Timestamping
(NF Z42-020 – Optional Technical Control)

## 1. Purpose

This project provides an **optional, tamper-evident capture journal** designed to support **NF Z42-020** requirements for trustworthy digitization processes.

⚠️ **Important**  
This feature is:
- **disabled by default**
- **optional**
- **limited in scope**

It applies **only to documents processed by the _Splitter_ module**.

Its purpose is to offer **additional technical guarantees** (integrity, traceability, chronology) for sensitive capture workflows where evidentiary value is required.

---

## 2. Scope and Applicability

### Enabled scope

When activated, this mechanism applies **exclusively** to:
- documents generated or finalized by the **Splitter module**

Other modules and document flows are **explicitly excluded**.

---

### Default behavior

By default:
- no journal is written
- no hashing is performed
- no timestamping is triggered

Activation could be done using workflow option

This ensures:
- no performance impact on standard flows
- no unintended legal commitments
- clear functional boundaries for audit

---

## 3. Compliance Positioning

This implementation:
- **does not claim full NF Z42-020 compliance**
- **supports** NF Z42-020 technical expectations for capture traceability
- is intended as a **defensive technical control**

Out of scope:
- SAE (NF Z42-020) archiving
- retention management
- legal destruction
- business process compliance

---

## 4. Architecture Overview

### Generated files (when enabled)

- `journal_scelle.json` # Global capture journal (append-only JSON)
- `journal_scelle.tsa.json` # RFC 3161 timestamp sealing evidence

These files exist **only if the option is enabled**.

### Location of files

Each file is stored in the application's designated data directory, typically:

```
/opt/edissyum/opencapture/evidences/custom/<CUSTOM_ID>/data/journal_scelle.json
/opt/edissyum/opencapture/evidences/custom/<CUSTOM_ID>/data/journal_scelle.tsa.json
```

---

## 5. Journal Design Principles

- Single global journal
- Append-only
- Cryptographically chained
- Periodically sealed
- Human-readable and machine-verifiable

The journal is global **per application instance**, not per document.

---

## 6. Journal Format (`journal_scelle.json`)

The journal is a **valid JSON document** containing a single root object with an array of entries.

## Exemple Entry

```json
{
  "index": 1,
  "timestamp": "2025-01-01T09:00:00+00:00",
  "event_type": "CAPTURE_COMPLETED",
  "module": "splitter",
  "document_id": "1", // Internal Open-Capture document identifier
  "file": {
      "original_name": "File 1.pdf", // Original filename at upload. Not used for processing, here just for traceability purposes.
      "sanitized_name": "File_1.pdf", // Filename after sanitization (if any). This one is used for processing.
      "stored_name": "20250101090000.pdf", // Actual stored filename (after renaming and storage in Open-Capture docservers)
      "stored_path": "/var/docservers/<CUSTOM_ID>/splitter/original_doc/2025/01012025_090000_d06ff0b125c147f99a73b7c06fdcd5d0.pdf"
  },
  "document_hash": {
      "algorithm": "SHA-256",
      "value": "a94a8fe5ccb19ba61c4c0873d391e987982fbbd3"
  },
  "previous_hash": "...",
  "current_hash": "..."
}
```

## 7. Certified Timestamp Sealing (`journal_scelle.tsa.json`)

### Purpose

To prove that the journal existed in a given state at a specific point in time.

### Mechanism

- The hash of the latest journal entry is submitted to a RFC 3161 Time Stamping Authority (TSA)
- The returned token is stored unchanged
- Tokens are Base64-encoded

### Structure

```json
{
  "scellements": [
    {
      "timestamp": "2025-01-01T09:05:00+00:00",
      "journal_index": 2, // Index of the latest journal entry
      "hash_sealed": "...", // Hash of the latest journal entry
      "algorithm": "SHA-256",
      "tsa_url": "https://freetsa.org/tsr",
      "tsr_base64": "MIAGCSqGSIb3DQEHAqCAMIACAQEx..." // Base64-encoded RFC 3161 token
    }
  ]
}
```

Each sealing operation freezes the entire journal history up to that index.

## 8. Cryptographic Guarantees

### 8.1 Hash chaining

Each entry includes:

- previous_hash
- current_hash

This ensures:

- detection of any modification
- detection of deletion
- strict chronological ordering

### 8.2 Document integrity

- Files may be renamed for storage purposes
- Hashes are computed after final storage
- Integrity is bound to content, not filenames

Renaming does not affect evidentiary value.

## 9. Time Handling

All timestamps are:

- UTC
- timezone-aware
- generated using modern Python APIs such as:

```python
datetime.now(UTC).isoformat()
```

This avoids ambiguity and deprecated behavior.

## 10. File Permissions and Security

Recommended permissions (Linux):

```bash
-rw-r-----  journal_scelle.json
-rw-r-----  journal_scelle.tsa.json
```

- Owner: application technical account
- Group: audit / supervision
- No write access for operators

Recommended hardening:

```bash
chattr +a journal_scelle.json
chattr +a journal_scelle.tsa.json
```

This enforces append-only behavior at filesystem level.
